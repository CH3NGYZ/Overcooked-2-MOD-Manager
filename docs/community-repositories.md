# 社区仓库、说明文档与安装版本绑定

## 官方源后的独立发现

首次教程门控同时控制官方源、代理源和社区发现。教程结束后继续原有官方源及子源加载；官方源树的 Raw 文件下载、解析及子源/仓库条目提交完成，并且初次代理配置提交完成后，立即并行启动 GitHub 与 Gitee 社区发现，不等待官方仓库的 Release API 刷新。官方网络失败且满足原有回退条件时，改为等待内置源树及其仓库条目提交完成，再按相同时机搜索。任一社区失败只显示该社区源的错误，不撤销官方仓库、代理配置或另一社区的结果。

启动、刷新全部仓库源和保存源后的整批刷新共用这个源文档完成节点。官方各仓库的 Release 仍在条目加入后独立刷新，与社区搜索及其后续 Release 请求并行；未完成的自定义源 Raw 请求不延迟官方源已经就绪的社区搜索。每个平台的搜索前只等待自身旧社区仓库的 Release 任务和已排队的配置快照，避免替换社区条目时复用旧结果，不等待官方或另一平台的 Release。源文档提交仍使用现有串行配置更新队列，所有完整 Dashboard 快照也使用同一队列。

每次点击“刷新全部仓库源”都重新执行两平台的社区发现，并刷新本轮社区仓库的 Release，不仅刷新官方/自定义 TOML 源，也不复用已经完成的社区搜索。搜索锁、取消标记、请求节流、分页、遮罩、错误及 Release 忙碌状态按平台隔离；一边搜索或验证时，不遮挡另一边已就绪仓库的安装按钮。社区搜索失败后，再次刷新全部仍会重新尝试，官方源保持独立刷新。

## GitHub API 发现

社区搜索使用 GitHub Search API 的 `topic:overcooked-2 topic:bepinex topic:mod` 查询，每页 10 项。每页先请求官方 API，再按当前已启用、地区适用的 GitHub API 代理顺序回退。配置中的用户 Token 只发送给官方 API，不发送给代理或 Raw 地址，也不借用管理器发布时的编译期凭据。

- 网络请求使用禁止缓存的请求头、5 秒单次超时和 2 MiB 响应上限。
- 分页以 `Link` 的下一页标记和 `total_count` 判断是否继续，下一页地址仍由可信 API 地址生成，不跟随响应提供的任意主机。
- 同一路由的搜索请求至少间隔 6.1 秒。`Retry-After`、`X-RateLimit-Remaining` 和 `X-RateLimit-Reset` 决定冷却；403/429 无有效时间时至少冷却一分钟，不立刻重试该路由。
- GitHub 搜索最多取前 1000 个结果。达到上限、`incomplete_results` 或条目缺失时明确提示，不把部分结果称为完整目录。
- 本轮所有可访问页面搜索完毕后，才通过现有仓库刷新入口并行读取 Release，社区最多同时刷新 4 个仓库。

GitHub 使用固定源 ID `github-community`，与官方源同级、显示在官方列表下方；仓库直接列出，不创建分类标题，不提供 MOD 简介按钮。界面从第 1 页开始，每页 10 项，标题中的分页按钮位于刷新按钮左侧。界面翻页只切换本轮目录，不重复调用 Search API。

列表始终显示安全提示：

> 以下为 GitHub 上带有 overcooked-2、bepinex、mod 标签的仓库，来源未知，安全性未知。请仔细检查仓库源码，再决定是否下载。

## Gitee 网页发现

Gitee 社区只在当前系统地区判定为中国大陆时搜索、展示或刷新，国际地区不创建验证 WebView，也不请求旧配置中的 Gitee 社区 Release、README 或安装。地区来自现有后端 `current_user_region`，不从界面语言或 IP 推测；GitHub、官方/自定义 Gitee 仓库不受社区限制影响。已安装 MOD 及其仓库绑定仍保留，不因地区变化删除。

Gitee 不调用仓库搜索 API，而是由独立 Tauri WebView 加载 `https://gitee.com/explore/topic/overcooked-2?page=1`。Windows 使用 WebView2 正常执行网页自己的验证脚本；普通 HTTP 客户端返回的 405 验证页不能当作空列表，也不通过复制验证脚本、硬编码 Cookie 或修改主窗口远程权限来绕过验证。

- WebView 初始隐藏、不抢焦点；8 秒仍未出现仓库列表时显示独立验证窗口，允许用户完成网页交互，关闭该窗口取消本平台搜索。每页最多等待 120 秒，超时显示错误。
- 导航只接受同协议、主机、端口及 Topic 路径，不允许认证信息、其他网页、新窗口、下载或网页权限申请。辅助窗口不授予 capability 或远程 IPC 权限，不能访问管理器命令；Rust 通过原生求值回调读取受限 DOM，不接收网页发起的应用命令。
- WebView 使用独立缓存目录 `~/OC2ModManager/cache/gitee-webview`，不共享管理器主窗口浏览器数据目录。搜索结束、异常、取消或超时后销毁辅助窗口；管理器主窗口实际销毁时也统一清理，不能让隐藏验证窗口阻止应用退出。不把 Cookie 或验证状态写入配置、日志或仓库。
- 只读取 `.explore-repo__list` 及分页节点，UTF-8 HTML 最多 2 MiB。仅从直属 `.explore-repo__list-item` 的项目链接提取 Owner/Repository，检查 Gitee 主机、路径片段和三 Topic 标签，排除头像、脚本、外站及无效链接；简介复用现有 `note` 区域。
- 后续页根据网页中可信 Topic 分页链接判断，由后端生成同站地址，不跟随任意主机。请求至少间隔 1 秒，最多 100 页、1000 个匹配仓库；达到安全上限或无法识别条目时明确提示，不冒称完整结果。
- 验证页未完成、网页结构改变或后续页失败时整轮失败，不提交部分目录或空成功。全部页面读取完成后，复用现有最多四个并行仓库 Release 刷新入口；Gitee Release 与 README 仍沿用原有网络逻辑，网页发现不替换它们的 API 或 Raw 请求。

Gitee 使用独立源 ID `gitee-community` 和配置字段 `gitee_community_discovery`，GitHub 原有 `community_discovery` 与仓库 ID 保持兼容。Gitee 与 GitHub 均使用独立分页，显示在官方源下方，每页 10 项；翻页只切换已经发现的目录，不重新请求网页。Gitee 列表显示对应的来源和安全提示：

> 以下为 Gitee 上带有 overcooked-2、bepinex、mod 标签的仓库，来源未知，安全性未知。请仔细检查仓库源码，再决定是否下载。

## 共用仓库规则

社区仓库 ID 由平台及大小写归一化后的 Owner/Repository 生成，和官方/自定义条目的身份空间隔离。同平台同 Owner/Repository 已被官方源或官方子源收录时，社区列表、计数与分页不再重复显示，大小写差异及官方条目的禁用状态不影响去重。自定义源同名条目及另一平台同坐标不冒充官方项目，社区默认规则不得覆盖官方资产规则、本地识别参数或简介。

官方归属按 `official-repository-index` 及其任意层级的 `parent_id` 关系判断，兼容已有内置根与仓库标记；不能仅依赖仓库自身的 `builtin` 权限字段。子源或仓库显式 `builtin=false` 不改变官方归属，也不会因去重重新获得编辑/删除保护。遍历不依赖源数组顺序，并以访问集合终止循环；无官方祖先的自定义源或孤立循环不参与官方去重。

双向时序共用同一身份规则：社区结果提交前，在现有配置提交锁内重新读取官方源树，已收录者不新增展示；官方仓库后到时，增量配置更新立即重新过滤社区列表、计数与分页，无需再次社区搜索。后端公共配置只过滤发现记录的输出副本，不删除持久化搜索记录或隐藏仓库；官方条目被移除后，仍保留的社区条目可以重新展示。MOD 状态链接使用同一官方源树定位规则。

社区默认资产规则匹配大小写不敏感的 DLL/ZIP。正则必须同时兼容 Rust 和 JavaScript；Rust 的 `(?i)` 不能直接交给浏览器的 `RegExp`。GitHub 自动生成的 Source code ZIP/TAR 使用 `zipball_url` / `tarball_url`，不进入 Release `assets`，因此不会作为 MOD 资产安装。Gitee 社区额外排除与当前 Release Tag 同名的源码 ZIP，例如 Tag 为 `v1.8.7.15` 时排除 `v1.8.7.15.zip`（ASCII 大小写不敏感），但保留 `Mod-v1.8.7.15.zip` 等正常附件；Release 解析、前端安装选项和后端显式资产选择共同保护旧缓存。这项过滤不改变官方/自定义仓库规则。已有 ZIP 安全解压、下载取消和安装回滚保持不变。

安装入口不因尚未刷新、没有 Release 或没有匹配资产而变成无反馈的禁用按钮。点击后分别提示先刷新、尚未发布 Release 或没有匹配的文件；刷新中、游戏运行中及真实操作忙碌仍禁止安装。实际安装菜单展示匹配规则的全部资产，不只取第一个 ZIP 或 DLL。

社区目录持久化到用户配置。已安装但本轮未返回的社区仓库保留作更新入口，并标注“已安装仓库，本轮未发现”。普通源刷新、源编辑和配置导入不得把受管理的社区源当作 TOML 源处理；导出的社区条目可导入成独立自定义仓库，不冒充受管理目录。

已安装的社区仓库后来被官方收录时，保留隐藏的社区配置及其 Release 刷新，用于原安装 Tag/频道的更新检测；不把 `all` 强行改绑到官方 `stable`/`beta`。MOD 状态链接可定位同项目的官方卡片，但这种显示路由不改变更新候选或安装清单。

MOD 管理的“最新版”和“有更新”状态链接先切换到目标社区仓库所在页，再展开仓库源并滚动定位。仓库页面高亮所有本次已展示的匹配卡片，即使官方与社区目标不能同时放进视口，也不丢弃社区高亮；键盘焦点和滚动仍定位首个目标。此规则仅用于仓库页面，不改变 MOD 管理列表的原有定位策略，其他状态标签仍不可点击。

## MOD 简介与仓库说明

这两个内容入口职责不同，不能合并：

- MOD 简介读取配置的 `note_i18n` / `note`，按当前语言选择。短内容直接显示；实际 Markdown 渲染高度超过 96 个逻辑像素时隐藏正文，并排显示“查看 MOD 简介”和“查看仓库说明”。
- 社区搜索有 `description` 时写入 `note`，直接在现有简介区域展示并经过同一安全渲染器；缺省或 null 时不显示。社区始终不新增“查看 MOD 简介”按钮，README 仍是独立仓库文档。
- 仓库说明读取默认分支根目录的 `README.md`。社区搜索提供默认分支，其他条目通过现有 API 顺序解析默认分支，不把文件安装模式的分支误当作仓库默认分支。
- GitHub README 使用现有 Raw 下载候选、排序和最多三路竞速协调器，直连优先，并使用配置中的 Raw 代理；Raw 下载不携带 API Token。
- Gitee README 明确使用 `https://gitee.com/{user}/{repository}/raw/{branch}/README.md`，一次单路直连 GET，不使用 GitHub Raw 代理、竞速协调器或 Range 分片。默认分支仍由真实仓库元数据确定，不固定猜测 main/master。
- 任一已发起候选返回 HTTP 404，立刻终止本次竞速、取消其他候选，并在对话框显示“文件不存在”；其他 HTTP/网络错误仍允许剩余候选胜出。
- README 限制为有效 UTF-8、最多 2 MiB，Raw 单次请求超时 30 秒。Markdown 经现有安全渲染器处理，外部链接通过类型化 IPC 在外部浏览器打开。
- 请求使用独立 ID 与取消标记；关闭、重开或切换仓库不影响 MOD 下载，也不能让迟到响应覆盖新说明。对话框沿用内容缩放、键盘焦点约束和关闭后焦点恢复。

Markdown 支持普通图片、链接徽章及安全的 HTML `img`。README 的相对路径按实际成功下载的 Raw URL（含真实分支）解析；仓库简介及 Release 日志使用已知分支上下文，不猜测默认分支。GitHub/Gitee 的 `blob` 图片链接转换为 Raw 图片地址；图片最大宽度为容器宽度，加载后重新测量简介折叠高度。

渲染仍使用 DOMPurify 的明确标签/属性白名单，拒绝脚本、事件处理器、内联样式、iframe、表单、内联 SVG、srcset、认证 URL 和危险协议。远程图片仅允许 HTTP(S)，通过 WebView 直接加载，不复用 README 的 Raw 代理竞速；第三方图片是否可见取决于实际网络。CSP 只扩展图片来源，不放宽脚本或 API 来源；文档外链仍通过现有类型化 IPC 打开。

## 所有来源优先记录 Owner/Repository/Tag

官方源、社区源和自定义仓库共用 `install_downloaded_repository`。Release 的新安装、重装及更新在同一安装清单事务中写入可缺省的 `repository_binding`：

```toml
[repository_binding]
provider = "github"
owner = "example"
repository = "my-mod"
tag = "v1.2.0"
channel = "all"
```

Owner/Repository/Tag 是主要绑定信息；provider 防止 GitHub/Gitee 同名仓库混淆，channel 保留安装时的 Release 频道。Tag 来自实际安装的 Release，不能从 DLL 版本、刷新后的最新版或文件安装模式补造。

本地扫描继续读取 GUID、DLL 版本、产品名和原始文件名，保留包/子 MOD、重复检测、禁用文件、备注和配置入口：

1. 有合法安装绑定时，优先按平台、Owner/Repository 和兼容频道匹配仓库；优先保留原安装源，其次匹配相同频道，再使用同项目的 `all` 条目。更新比较使用已安装 Tag，不用 DLL 版本覆盖它。
2. 没有合法绑定的旧清单和手工 DLL 继续按现有 GUID、产品名、文件名及 `version_regex` 识别，按 DLL 版本检测更新。安装清单的新字段可缺省，旧数据不强制迁移。
3. 相同 Tag 为最新版；可解析版本只提示更高远端版本，避免降级提示；无法解析的非 SemVer Tag 按精确差异判断更新。草稿、错误缓存和其他频道不能确认更新状态。
4. 绑定信息保留但仓库未加载时，显示“已绑定仓库未加载，无法检测更新”，不改绑到恰好匹配 DLL 元数据的其他项目。

绑定随安装包清单及回收站快照保存，不改变文件操作的包身份。旧源消失且同项目只对应一个孤立包时，新条目的安装/卸载可复用该包 ID；仍在配置中的其他包不会仅因坐标相同被合并。多个孤立包存在歧义时，先提示用户在 MOD 管理中确认。

包和子 MOD 的启停、卸载、恢复仍使用完整成员及真实路径。升级回收保留原绑定，新包提交成功后才替换绑定；分项恢复必须核对活动清单的 Tag、绑定和安装时间，拒绝将旧文件合并到已更换来源的包。
